# РОЗДІЛ 1. АНАЛІЗ ПРЕДМЕТНОЇ ОБЛАСТІ ТА ТЕХНІЧНЕ ЗАВДАННЯ

## 1.1. Інженерний опис існуючих систем-аналогів

Для обґрунтування доцільності розробки системи UseTrace Studio було проведено системний аналіз трьох програмних продуктів-аналогів, що застосовуються в індустрії для управління вимогами та архітектурного моделювання.

### 1. Enterprise Architect (Sparx Systems)
- **Архітектурний патерн та масштабованість:** Продукт реалізовано на базі класичного патерну Fat Client / Desktop Monolith. Обчислювальна бізнес-логіка та валідація моделей виконуються безпосередньо на робочій станції користувача. Можливості горизонтального масштабування клієнтського рівня відсутні. При збільшенні обсягу даних виникає зниження пропускної здатності мережевого каналу через вибірку великих масивів реляційних даних.
- **Протоколи передачі даних:** Застосовуються прямі інтерфейси підключення до баз даних (ODBC, OLE DB), шлюз Pro Cloud Server Gateway (HTTP/HTTPS, JSON/XML) та REST API на основі специфікації OSLC. Підтримка дуплексного стримінгу стану (WebSockets, gRPC) відсутня.
- **Базовий стек даних та консистентність:** Організація зберігання здійснюється в реляційних СУБД (PostgreSQL, Microsoft SQL Server, Oracle). Забезпечується рівень транзакційності ACID. Застосовується песимістичне блокування пакетів (Package Locking), яке обмежує паралельний запис з інших сесій до обраного піддерева моделей.
- **Критичні інженерні недоліки (Technical Bottlenecks):** Реляційна схема даних (таблиці t_object, t_connector) не оптимізована для обходу графових структур, що призводить до падіння продуктивності (I/O bottlenecks) при виконанні складних JOIN-запитів. Песимістичне блокування створює блокуючі затори при паралельній розробці в команді.

### 2. Jama Connect
- **Архітектурний патерн та масштабованість:** Систему побудовано за багатошаровою веб-архітектурою на базі JVM (Spring Framework) із подієво-орієнтованими компонентами (Event-Driven Integration). Безстатусні (stateless) веб-сервери піддаються горизонтальному масштабуванню, проте центральна СУБД стає вузьким місцем під час масового імпорту артефактів.
- **Протоколи передачі даних:** Взаємодія здійснюється через RESTful API (HTTP/HTTPS, JSON), асинхронні брокери повідомлень (ActiveMQ, Apache Kafka) та механізм Webhooks.
- **Базовий стек даних та консистентність:** Первинним сховищем є реляційні СУБД (PostgreSQL, Microsoft SQL Server). Вторинне сховище — Elasticsearch (NoSQL / Inverted Index). Застосовується модель Hybrid Consistency: ACID для первинного запису та Eventual Consistency для відображення оновлених пошукових індексів.
- **Критичні інженерні недоліки (Technical Bottlenecks):** Спостерігається затримка синхронізації індексів (Indexing Latency Lag) при виконанні пакетних операцій. Відзначається висока обчислювальна складність рекурсивного обходу дерев вимог засобами СУБД та висока ресурсомісткість серверного середовища виконання JVM.

### 3. ReqView
- **Архітектурний патерн та масштабованість:** Продукт спроєктовано як Local-First / Offline-First Desktop Application на базі фреймворку Electron (Node.js із C++ модулями). Командна співпраця реалізується через синхронізацію файлових артефактів у зовнішніх системах контролю версій (Git, SVN).
- **Протоколи передачі даних:** Використовується локальне введення-виведення (JSON/XML файли), SSH/HTTPS для взаємодії з Git-репозиторіями, а також інтерфейс CLI та локальний REST API. Мережеві сокети WebSockets/gRPC для обміну дельтами змін у реальному часі відсутні.
- **Базовий стек даних та консистентність:** Застосовується In-Memory Document Store. Граф вимог повністю утримується в оперативній пам'яті (In-Memory DOM structure) та періодично зберігається на диск у вигляді JSON-структур. Консистентність у межах сеансу забезпечується однопотоковим Event Loop Node.js. Конфлікти паралельної розробки вирішуються за допомогою Git 3-way merge.
- **Критичні інженерні недоліки (Technical Bottlenecks):** Наявні апаратні обмеження оперативної пам'яті (Memory-Bound Scaling) та затримки виконання через паузи Garbage Collector при роботі з великими файлами. Відсутність атомарних блокувань викликає Git merge-конфлікти, що унеможливлює реактивне сумісне редагування (live-editing) та призводить до затискання головного потоку виконання (UI Thread lock).

### Аналітичний висновок підрозділу 1.2

Проведений критичний аналіз архітектурних рішень систем-аналогів (Enterprise Architect, Jama Connect, ReqView) виявив низку фундаментальних інженерних обмежень, які унеможливлюють ефективне сумісне моделювання вимог у сучасних розподілених командах. Застосування застарілого патерну «Fat-Client Desktop Monolith» у поєднанні з реляційними схемами даних, не оптимізованими під графові структури, призводить до високої затримки (latency) при складних рекурсивних вибірках та жорстко обмежує паралельну розробку через песимістичне блокування пакетів. Автономні Electron-рішення з локальним утриманням моделей у пам'яті (In-Memory DOM Store) стикаються з критичними апаратними бар'єрами (Memory-Bound Scaling), блокуваннями головного потоку виконання (UI Thread lock) та паузами збирача сміття (Garbage Collector), а відсутність атомарних блокувань викликає нерозв'язні текстові конфлікти при Git-синхронізації. Своєю чергою, навіть важковагові веб-платформи на базі JVM з гібридною моделлю консистентності (PostgreSQL + Elasticsearch) порушують цілісність відображення трасуваності через часову затримку асинхронної індексації (Indexing Latency Lag). При цьому повна відсутність дуплексних реактивних протоколів у всіх аналогах унеможливлює наскрізну двосторонню синхронізацію моделей та верифікаційного беклогу в режимі реального часу.

Для усунення визначених системних дефектів у розроблюваній веб-системі «UseTrace Studio» передбачено реалізацію Clean Architecture у поєднанні з мікросервісною веб-архітектурою, що чітко розмежовує обчислювальні контексти. Застосування асинхронного ASGI-фреймворку FastAPI гарантує високу пропускну спроможність та неблокуюче введення-виведення (Non-blocking I/O) при мінімальних інфраструктурних витратах. Винесення обчислень топології вимог, оцінки трудовитрат та трасувальних зв'язків у локальний In-Memory DAG-двигун на основі бібліотеки NetworkX дозволяє виконувати алгоритми обходу орієнтованих ациклічних графів із часовою складністю O(V+E), знімаючи рекурсивне обчислювальне навантаження з реляційного сховища PostgreSQL (SQLAlchemy v2). Впровадження дуплексного протоколу WebSockets забезпечує двосторонню синхронізацію стану між клієнтом та сервером без затримок синхронного опитування (polling), тоді як використання Mermaid.js переносить процеси рендерингу UML-діаграм на сторону клієнта (Vue 3) шляхом трансляції легковагового DSL-коду.

Таким чином, результати порівняльного аналізу доводять недоцільність запозичення архітектурних шаблонів розглянутих продуктів та повністю обґрунтовують технічну необхідність розробки програмного комплексу «UseTrace Studio». Обраний технологічний стек створює оптимальний баланс між строгою транзакційною консистентністю даних (ACID) та високопродуктивним обробленням графових моделей у реальному часі. Отримані висновки та сформульовані технічні вимоги є безпосереднім підґрунтям для Розділу 2 («Проєктування»), у якому буде розроблено контейнерні та компонентні архітектурні моделі системи (C4 Model), визначено специфікацію REST/WebSocket API, а також спроєктовано ER-діаграму бази даних і структуру DAG-обчислень.
