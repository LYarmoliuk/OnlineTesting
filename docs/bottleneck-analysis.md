# Аналіз потенційних вузьких місць OnlineTesting

## 1. Мета

Мета аналізу — визначити компоненти, які потенційно можуть обмежувати продуктивність платформи під час одночасного проходження тестів великою кількістю користувачів.

Наведені нижче значення є теоретичним сценарієм для архітектурного аналізу, а не результатами проведеного навантажувального тестування.

## 2. Сценарій навантаження

Припустимо, що 500 студентів одночасно проходять тест із 40 запитань.

- Кількість одночасних користувачів: 500.
- Запитань на одного користувача: 40.
- Потенційна кількість операцій надсилання відповідей: до 20 000, якщо кожна відповідь зберігається окремо.
- Додатково виникають запити на завантаження тесту, початок і завершення спроби.

Фактична кількість запитів і час виконання залежатимуть від реалізації проходження тесту, пакетування операцій, мережі та конфігурації інфраструктури.

## 3. Потенційні вузькі місця

### PostgreSQL: конкурентний запис
Велика кількість одночасних записів може збільшити затримки та конкуренцію за ресурси бази даних.

Можливі заходи:
- використовувати пакетне збереження там, де це виправдано;
- перевірити індекси для часто використовуваних зовнішніх ключів;
- аналізувати повільні SQL-запити;
- вимірювати використання з'єднань і дискового введення-виведення.

### Надмірне завантаження даних
Якщо endpoint завантажує забагато пов'язаних сутностей або виконує багато окремих запитів, зростають затримки й обсяг переданих даних.

Можливі заходи:
- повертати DTO з потрібними полями;
- уникати N+1-запитів;
- застосовувати пагінацію для великих списків;
- завантажувати дані за потреби.

### Пул з'єднань
Під час пікового навантаження API може очікувати вільне з'єднання з базою даних.

Можливі заходи:
- перевірити налаштування пулу Npgsql;
- вимірювати кількість активних з'єднань;
- не утримувати з'єднання довше, ніж потрібно.

### Обчислення результатів
Якщо в майбутньому додати складне оцінювання великої кількості спроб, обчислення можуть збільшити використання процесора.

Можливі заходи:
- оптимізувати алгоритми оцінювання;
- не виконувати однакові обчислення повторно;
- за потреби винести важкі фонові операції в окремий процес.

## 4. Метрики для вимірювання

Для реального навантажувального тестування варто збирати:

- пропускну здатність (запити за секунду);
- середню затримку та перцентиль p95/p99;
- частку HTTP-помилок і тайм-аутів;
- використання CPU та пам'яті;
- кількість активних з'єднань із PostgreSQL;
- час виконання SQL-запитів;
- дискове введення-виведення.

## 5. План перевірки

1. Створити контрольний сценарій із поступовим збільшенням кількості віртуальних користувачів.
2. Виміряти базові показники за низького навантаження.
3. Збільшувати навантаження до цільових 500 одночасних користувачів.
4. Зафіксувати затримки, помилки та ресурси, що насичуються першими.
5. Застосувати оптимізацію й повторити вимірювання за тих самих умов.

Для відтворюваності потрібно документувати конфігурацію обладнання, версії програмного забезпечення, параметри навантаження та тривалість тесту.

## 6. Висновок

Найімовірніші потенційні обмеження за значного навантаження — конкурентний запис у PostgreSQL, неефективне завантаження пов'язаних даних і вичерпання пулу з'єднань. Ці припущення необхідно перевірити вимірюваннями. Без виконаного навантажувального тесту не можна стверджувати, що конкретний bottleneck уже підтверджено.
