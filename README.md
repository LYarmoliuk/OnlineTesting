
# OnlineTesting

## 1. Опис проєкту

OnlineTesting — вебсистема для створення та проходження онлайн-тестів.

Система дозволяє організатору створювати тести, додавати запитання та варіанти відповідей, публікувати тести.

Студенти можуть проходити опубліковані тести, зберігати відповіді та отримувати результати оцінювання.

## 2. Технології

- Backend: ASP.NET Core 10, C#
- Frontend: Vue 3, TypeScript, Vite
- Database: PostgreSQL 17
- ORM: Entity Framework Core
- Контейнеризація: Docker, Docker Compose
- Вебсервер frontend: Nginx
- API: REST, JSON, HTTP

## 3. Архітектура системи

Поточна конфігурація запускає три однакові API-вузли зі спільною PostgreSQL:

1. Frontend — інтерфейс організатора та студента.
2. Backend — взаємозамінні REST API-вузли `api_a`, `api_b` та `api_c` у приватній Docker-мережі.
3. PostgreSQL — зберігання даних.

Схема взаємодії:

```text
Організатор / Студент
          |
          | HTTP :8081
          v
     Vue 3 + Nginx
          |
          | HTTP /api/*
          v
   Nginx балансування
       /     |     \
 API api-a    API api-b    API api-c
       \         |         /
        PostgreSQL 17
          |
          v
 Docker Volume: postgres_data
```

Усі контейнери підключені до мережі `testing-network`. Nginx розподіляє `/api/` між трьома API-вузлами без прив'язки клієнта до вузла. Публікується тільки порт фронтенду; API і база даних не мають зовнішніх портів.

Зовнішні інтеграції та черги повідомлень у поточній версії відсутні.

## 4. Доменна модель

Основні сутності:

- Test — тест, його назва, опис та статус публікації.
- Question — запитання, яке належить тесту.
- AnswerOption — варіант відповіді на запитання.
- TestAttempt — спроба проходження тесту.
- StudentAnswer — відповідь студента в межах спроби.

Зв'язки:

- Test 1:N Question
- Question 1:N AnswerOption
- Test 1:N TestAttempt
- TestAttempt 1:N StudentAnswer
- Question 1:N StudentAnswer

Дані зберігаються в PostgreSQL.

## 5. REST API

| Метод | Endpoint | Призначення |
|---|---|---|
| GET | /api/tests | Отримати список тестів |
| POST | /api/tests | Створити тест |
| PUT | /api/tests/{id} | Оновити тест або статус публікації |
| DELETE | /api/tests/{id} | Видалити тест |
| GET | /api/tests/{testId}/questions | Отримати запитання тесту |
| POST | /api/tests/{testId}/questions | Додати запитання |
| PUT | /api/questions/{id} | Оновити запитання |
| DELETE | /api/questions/{id} | Видалити запитання |
| GET | /api/questions/{questionId}/options | Отримати варіанти відповідей |
| POST | /api/questions/{questionId}/options | Додати варіант |
| POST | /api/tests/{testId}/attempts | Почати проходження тесту |
| PUT | /api/attempts/{attemptId}/answers | Зберегти відповідь |
| POST | /api/attempts/{attemptId}/submit | Завершити тест і обчислити результат |
| GET | /api/attempts/{attemptId}/result | Отримати результат |

API використовує HTTP-статуси 200, 201, 204, 400, 404, 409 залежно від операції та результату її виконання.

Для роботи із захищеними endpoint спроб використовується заголовок X-Attempt-Token.

## 6. Запуск системи

Необхідне програмне забезпечення:

- Docker Desktop
- Docker Compose

Перед запуском створити файл `.env` у корені проєкту:

```env
DB_PASSWORD=your_local_password
```

Запустити систему:

```bash
docker compose up -d --build
```

Адреси:

- Застосунок: http://localhost:8081 (або порт `LAB3_PUBLIC_PORT` із `.env`)
- API через Nginx: http://localhost:8081/api/
- Перевірка стану: http://localhost:8081/health

Три API-вузли (`api_a`, `api_b`, `api_c`) працюють усередині Docker-мережі. Сервіс `migrate` застосовує міграції бази даних перед їх запуском.

Перевірити контейнери:

```bash
docker compose ps
```

Переглянути журнали:

```bash
docker compose logs -f frontend api_a api_b api_c db
```

Зупинити систему:

```bash
docker compose down
```

Дані PostgreSQL зберігаються в Docker volume postgres_data.

Не використовувати `docker compose down -v`, якщо потрібно зберегти дані.

## 7. Піковий сценарій навантаження

Потенційний сценарій високого навантаження — одночасне проходження тесту великою кількістю студентів.

Кожен студент виконує послідовність:

1. POST /api/tests/{testId}/attempts
2. Багаторазові PUT /api/attempts/{attemptId}/answers
3. POST /api/attempts/{attemptId}/submit
4. GET /api/attempts/{attemptId}/result

Найбільше навантаження створюють масові записи відповідей та одночасне завершення тестів.

## 8. Bottleneck Analysis

### 8.1. Збереження відповідей

Компонент: PUT /api/attempts/{id}/answers

Причина: велика кількість одночасних SQL-операцій запису, обмеження дискового I/O та пулу з'єднань.

Симптоми: зростання p99 latency, зниження RPS, очікування вільних з'єднань.

Можливе рішення: оптимізація SQL-запитів, індексація, налаштування пулу з'єднань.

### 8.2. Обчислення результатів

Компонент: POST /api/attempts/{id}/submit

Причина: одночасне завантаження відповідей і підрахунок балів для багатьох спроб.

Симптоми: підвищене використання CPU, зростання часу відповіді.

Можливе рішення: оптимізація запитів EF Core та вибірка тільки необхідних даних.

### 8.3. Єдиний сервер PostgreSQL

Компонент: PostgreSQL 17

Причина: усі операції читання та запису обслуговуються одним екземпляром БД.

Симптоми: I/O Wait, повільні SQL-запити, вичерпання доступних з'єднань.

Можливе рішення: індексація, оптимізація конфігурації БД, масштабування читання за потреби.

## 11. Лабораторна робота 2 — архітектура без локального бізнес-стану

### 11.1. Аудит стану

| Категорія | Дані або конструкція | Де зберігаються / висновок |
|---|---|---|
| Ephemeral / Local Safe | Локальні змінні запиту, DTO, обчислення балів, EF Core change tracker, журнали | Існують лише під час запиту; після нього не потрібні для наступного вузла. |
| Shared / Externalized | Тести, запитання, варіанти, спроби, відповіді, токени доступу, статус і результат | PostgreSQL; базовий API і майбутні два вузли працюють з однією БД. |
| Critical Stateful Dependencies | Sticky sessions, серверні сесії, локальний кеш, singleton-колекції, локальні блокування, файловий стан | У бізнес-логіці відсутні. Демонстраційний `WeatherForecast` зі статичним масивом вилучено. |

Окремий Redis не потрібен: у системі немає серверного сесійного кешу, а PostgreSQL уже є спільним довговічним сховищем. `X-Attempt-Token` передається в кожному запиті до спроби; токен зберігається разом зі спробою в БД. `INSTANCE_ID` використовується лише для діагностики та повертається в заголовку `X-Instance-ID`.

Раніше `PUT /answers` і `POST /submit` читали та змінювали спробу незалежно. Паралельні запити могли одночасно створити відповідь або завершити спробу під час її оновлення. Тепер обидві операції виконуються в транзакції PostgreSQL із блокуванням рядка відповідної спроби (`SELECT ... FOR UPDATE`). Запити до однієї спроби впорядковуються між вузлами; обмеження унікальності `(TestAttemptId, QuestionId)` лишається додатковим захистом. Якщо API-процес завершується до commit, PostgreSQL відкочує транзакцію; після commit дані доступні другому вузлу.

### 11.2. Потік запиту збереження відповіді

1. Клієнт надсилає `PUT /api/attempts/{id}/answers`, заголовок `X-Attempt-Token` і JSON з `questionId`, `selectedOptionId`.
2. Будь-який API-вузол починає транзакцію, знаходить спробу за `id` і токеном у PostgreSQL та блокує її рядок до завершення транзакції.
3. Вузол перевіряє статус спроби й належність запитання та варіанта, читає поточну відповідь із БД.
4. Вузол додає або змінює відповідь, зберігає її та завершує транзакцію. У відповідь повертається `204` і заголовок `X-Instance-ID`.
5. Наступний запит, навіть на іншому вузлі, читає актуальні дані з PostgreSQL. Після запиту в процесі не залишається потрібного для продовження бізнес-стану.

Схеми C4 Container і C4 Component, а також послідовність запиту наведено в [docs/architecture.md](docs/architecture.md).

### 12.2. Запуск і перевірка

### 12.3. Результати вимірювання

Прогони виконано **1 листопада 2026 року** на одному комп'ютері: 240 GET-запитів із паралельністю 24, один прогін на конфігурацію. `RPS` — успішні відповіді за секунду; `p99` — 99-й перцентиль часу клієнтського запиту. У всіх п'яти прогонах отримано 240/240 HTTP 200.

| Конфігурація | Алгоритм | RPS | p99, мс | Розподіл `api-a / api-b / api-c` |
|---|---|---:|---:|---:|
| 1 вузол | Round Robin | 84,82 | 78,28 | 240 / 0 / 0 |
| 2 вузли | Round Robin | 95,04 | 37,83 | 120 / 120 / 0 |
| 3 вузли | Round Robin | 145,21 | 32,92 | 80 / 80 / 80 |
| 3 вузли, `api_b` +250 мс | Round Robin | 78,61 | 283,58 | 80 / 80 / 80 |
| 3 вузли, `api_b` +250 мс | Least Connections | 84,59 | 259,98 | 114 / 10 / 116 |

Від 1 до 3 вузлів пропускна спроможність цього синтетичного сценарію зросла приблизно на **71%**. За наявності повільного вузла Least Connections надсилав йому 10 замість 80 запитів; RPS зріс приблизно на **7,6%**, а p99 зменшився приблизно на **8,3%** порівняно з Round Robin. Отже, Round Robin дає рівномірний розподіл за подібних вузлів, а Least Connections краще підходить, коли один вузол довше обробляє запити. Один прогін на конфігурацію не є статистичною оцінкою стабільності цих відмінностей.

`GET /api/benchmark` — синтетичний read-only endpoint без SQL-запиту. Затримка через `Task.Delay` моделює довшу обробку, а не завантаження CPU. Тому ці цифри описують саме балансування й цей комп'ютер, а не продуктивність реального тестування студентів.

### 12.4. Відмова вузла, health check і відновлення

`scripts/verify-lab3-platform.ps1` перевіряє єдиний публічний порт і розподіл між трьома `X-Instance-ID`, запускає потік із 400 GET-запитів до `/api/tests`, зупиняє `api_b` **під час** цього потоку та повертає вузол у роботу. У прогоні 1 листопада 2026 року **104 запити почалися до зупинки, 296 — після; 400/400 завершилися HTTP 200, без 5xx**. Після запуску `api_b` знову з'явився в розподілі. Скрипт відновлює контейнер навіть при невдалій перевірці.

Окремий `scripts/verify-lab3-degraded.ps1` тимчасово запускає `api_b` з недоступним для нього підключенням до БД. Його `/health` повертає 503, а DB-залежний `/api/tests` — помилку; через Nginx **40/40 запитів до кожного маршруту** отримали 200 від `api_a` або `api_c`. Скрипт відновлює правильне підключення `api_b`. Це **пасивна** перевірка: відкритий Nginx не опитує upstream `/health` за розкладом. Він виявляє несправність, коли надходить запит. Просто повільний, але успішний вузол не виключається з пулу; для такого профілю Least Connections зменшує його частку трафіку.

Повторна передача після помилки безпечна для GET. Для POST/PUT, якщо запит уже було надіслано вузлу, автоматичне повторення без гарантії ідемпотентності не використовується. Тому перевірка 400/400 стосується GET і не є обіцянкою нульових втрат для всіх операцій запису.

### 12.5. Наступне вузьке місце та доступність балансувальника

За архітектурою **спільна PostgreSQL — наступний кандидат на обмеження** під час реального проходження тестів: кожен API-вузол звертається до однієї БД, а збереження відповідей і завершення спроб використовують транзакції та блокування рядків. Додавання API-вузлів збільшує сумарну конкуренцію за пул з'єднань, CPU й дисковий I/O БД. Для підтвердження потрібен окремий тест із записом відповідей, метрики активних з'єднань, очікування блокувань, CPU та часу SQL-запитів. Поточний синтетичний endpoint не дозволяє оголосити PostgreSQL **виміряним** bottleneck. Детальні гіпотези наведено в [docs/bottleneck-analysis.md](docs/bottleneck-analysis.md).

Сам Nginx — Single Point of Failure: якщо його контейнер або хост недоступний, клієнт втрачає єдину точку входу, хоча API-вузли працюють. Для високої доступності потрібні два балансувальники й перемикання зовнішньої адреси, наприклад Keepalived/VRRP; альтернативи на кшталт DNS Round Robin мають інші затримки перемикання. У цьому лабораторному Compose резервного балансувальника немає.

### 12.6. Демонстрація на захисті

1. `docker compose ps` і `docker compose config --format json`: показати три API-вузли, спільну БД та один публічний порт.
2. Кілька разів викликати `curl.exe -i http://localhost:8081/health`: показати різні `X-Instance-ID`.
3. Запустити `pwsh -NoProfile -File scripts/verify-lab3-platform.ps1`: показати живу зупинку, 400/400 успішних GET і відновлення вузла.
4. Запустити `pwsh -NoProfile -File scripts/verify-lab3-degraded.ps1`: показати виключення вузла з недоступною БД й автоматичне відновлення.
5. Запустити `pwsh -NoProfile -File scripts/run-lab3-experiments.ps1 -Requests 240 -Concurrency 24`: скрипт перемикає Nginx із Round Robin на Least Connections без перебудови образу, показує RPS, p99 і розподіл, потім повертає Round Robin та три вузли.
6. Пояснити за таблицею вище вибір алгоритму, межі пасивного health check, наступний кандидат на bottleneck і Single Point of Failure балансувальника.
